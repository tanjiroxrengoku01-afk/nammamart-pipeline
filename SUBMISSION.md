## Part A: ETL pipeline

`dags/nammamart_etl_slick.py`, helpers in `include/nammamart_helpers/` (`quality_rules.py`, `etl_steps.py`).

`extract_orders | extract_payments | extract_customers | extract_products | extract_stores` (parallel) -> `validate` -> `transform` -> `load` -> `reconcile_payments` -> `report` -> `audit_run`

- **Validate:** 40 rules in Python. Rows that fail a Critical rule go to `include/quarantine/slick/<file>_failed_<run_id>.csv` with `failure_reason`, `_source_file` and `_source_row`. Email and phone are masked in the quarantine copy as well. The same rows are also logged one row per broken rule in `etl_rejected_rows`.
- **Transform:** trims values, upper-cases status, maps `upi`, `UPI `, `CARD` and `cod` to the allowed values, and fixes tier casing. Customers and products are de-duplicated (first row wins). Email and phone are masked (`pr***@example.com`, `98******21`). Orders are joined to products for `cost_price`. The step derives `order_date`, `net_revenue`, `gross_margin` and `within_15_min`.
- **Load:** star schema `etl_fact_orders` + `etl_dim_customer`, `etl_dim_product` and `etl_dim_store`. All four tables load in one transaction. The load is idempotent: delete the incoming keys, then insert. An order that turns bad on a later run is also deleted. Guards fail the run if there are duplicate `order_id`s or facts without a dimension row.
- **Repaired dimension members:** a dimension row that fails a Critical rule is quarantined. If clean orders still point at it, it is loaded as `REPAIRED` with only the bad field neutralised. Example: store S07 has a blank zone, so it loads as zone `Unknown` and its orders keep their revenue (₹82,725.60 in September).
- **Reconcile:** `etl_payment_reconciliation` holds one row per mismatch, with a reason (`AMOUNT_MISMATCH`, `PAYMENT_FAILED`, `NO_PAYMENT_RECORD`, `RETURNED_NOT_REFUNDED`, `ORDER_NOT_IN_CLEAN_ORDERS`, ...).
- **Report:** builds `etl_daily_zone_revenue` and `etl_category_margin` and prints them in the task log.

## Part C: Scheduling

```python
schedule="0 9 * * 1-6"
start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Kolkata")
catchup=False
default_args={"retries": 2, "retry_delay": timedelta(minutes=1), "execution_timeout": timedelta(minutes=10)}
max_active_runs=1
```

- **retries=2, retry_delay=1 min:** covers short problems such as a file still being copied or the DuckDB file locked by the other DAG. Three tries take about 2 minutes, so a real failure still shows up long before the 9:30 meeting.
- **execution_timeout=10 min:** a full run takes about 30 seconds, so a task running 10 minutes is stuck. It gets killed and retried instead of hanging past 9:30.
- **catchup=False:** each run reads the current state of the export files. The files have no date partition, so replaying every missed day would load the same files again and add nothing. Missed days are covered by the next run, because the load is an upsert.
- **max_active_runs=1:** two runs of the same DAG never write to the warehouse at the same time.

**Answers**

1. **Cron expression:** `0 9 * * 1-6`, meaning minute 0, hour 9, Monday (1) to Saturday (6), in the DAG's timezone (Asia/Kolkata).
2. **Time in UTC in the Airflow UI:** 03:30 UTC, since IST is UTC+5:30 with no daylight saving. The scheduled runs show it in their ids, for example `scheduled__2026-10-22T03:30:00+00:00`. The UI can display either UTC or IST.
3. **If `start_date` were left in UTC:** the cron would be read in UTC and the run would start at 09:00 UTC, which is 14:30 IST. That is five hours after Kavya's 9:30 meeting, so the report would always be late.
4. **If the laptop or Docker is off at 9 AM:** the scheduler isn't running, so nothing runs and the data isn't ready. When Airflow starts again, `catchup=False` creates only the latest missed run, not one per missed day, and it runs straight away. For production it needs an always-on host (a cloud VM or managed Airflow), plus a missed-SLA alert.

### Questions

1. **Ownership.** Each file is owned by the team that runs the source system:
   - orders: Operations (order management system)
   - payments: Finance (payment gateway)
   - customers: CRM / Marketing; they are also the PII data owner, under the DPO
   - products: Category / Catalogue team
   - stores: Store Operations

   The data team (FDE now, data engineers later) owns the pipelines and warehouse tables as data custodian. Each mart has a business owner: Finance owns reconciliation and revenue, Ops owns delivery SLA. A change to a quality rule such as the 120-minute limit is proposed by the data team. It is approved by the owner of the KPI it affects (COO Kavya for delivery), and Finance signs off if revenue changes. It ships as a reviewed code change, because the rule lives in `quality_rules.py`.
2. **Data dictionary:** see above.
3. **Lineage.** Example number: `mart_daily_store_kpis` for **store S01 on 2026-09-15** shows net_revenue **₹4,583.05** (6 delivered orders).
   - **ELT:** `SELECT order_id, _source_file, _source_row, _run_id FROM mart_fact_orders WHERE order_date = ... AND store_id = ... AND order_status = 'DELIVERED'` lists the 6 orders. Each one's `_source_file`, `_source_row` and `_run_id` locate the exact untouched row in `raw_orders`, for example ORD001127 ₹597.55 is `orders.csv` line 89, ORD001105 line 391, ORD001130 line 751, ORD001144 line 1499, ORD001133 line 1724 and ORD001132 line 2192, all from run `final2_elt`. 597.55 + 360.00 + 447.30 + 354.00 + 2,325.60 + 498.60 = 4,583.05. `SELECT * FROM raw_orders WHERE _run_id = 'final2_elt' AND _source_row = 89` returns the untouched source row. That is the whole chain, in SQL, inside the warehouse.
   - **ETL:** the fact has `order_id` and `loaded_run_id` but no source row. To prove it, I have to re-read `orders.csv` and hope the file hasn't changed since. Rows that weren't loaded are traceable (the quarantine file has `_source_file` and `_source_row`); loaded rows aren't.
   - **ELT is easier,** because raw is kept forever with lineage columns and every step is a SQL view of the step before.
4. **Personal data.**
   - Columns: `customers.full_name`, `email` and `phone` are direct identifiers. `area`, `pincode`, `city` and `customer_id` are quasi-identifiers or pseudonymous, and `stores.manager_name` is employee personal data.
   - Masking: email becomes `pr***@example.com` and phone `98******21`, in Python (`mask_email`/`mask_phone`) and SQL (`mask_email`/`mask_phone` macros). The masked form is the only form in staging, marts, the ETL dimension and the quarantine files. Raw email and phone exist only in `raw_customers`.
   - Why mask, not delete: support staff can still match "the customer ending 21" on a call, duplicates and data-quality issues stay visible, and the reports still work.
   - The law: the **Digital Personal Data Protection Act, 2023 (DPDP Act)** and its Rules. NammaMart is a *Data Fiduciary* and must:
     - collect data only for a stated purpose with notice and consent;
     - use only what that purpose needs (data minimisation);
     - keep it accurate, protect it with reasonable security safeguards, and report breaches to the Data Protection Board and the affected people;
     - erase it when the purpose is served or consent is withdrawn;
     - honour data principals' rights to access, correction and erasure.

     Penalties go up to ₹250 crore per breach.
   - Known gap: `full_name` is still unmasked in `etl_dim_customer` and `stg_customers`. The marts don't show it, but it should move to a restricted table or be pseudonymised.
5. **Access control.**

   | Layer | Who can read |
   |---|---|
   | Raw | Data engineers and the compliance auditor only, through a separate role |
   | Staging | Data engineers and analysts |
   | Marts | Business users: Finance, Ops, leadership |
   | Quarantine (files, `etl_rejected_rows`, `stg_rejected_rows`) | Data engineers and the owner of the source file, so they can fix it |

   Unmasked phone numbers in `raw_customers` should be visible to almost no one: the pipeline service account and, on a logged, ticketed request, the DPO or customer-support lead. In production I would encrypt raw PII columns or split them into a separate locked schema. DuckDB has no row or column grants, so this needs a warehouse such as Postgres, BigQuery or Snowflake.
6. **Retention.**

   | Data | Keep for | Then |
   |---|---|---|
   | Raw orders and payments | 8 years, the statutory limit for financial records | Archive to cold storage, then delete |
   | Raw customers (unmasked) | Only while the account is active (plus a short grace period) | Erase or anonymise on account closure or consent withdrawal, as the DPDP Act requires |
   | Quarantine files and rejected rows | 90 days, enough to fix and replay | Delete |
   | Masked customer data in marts | While the customer is active | Anonymise (drop customer_id link) |
   | `dq_results` / `pipeline_runs` | Indefinitely | No PII; it is the audit trail |
7. **Secrets.** There are no credentials in the code. The only "connection" is a local DuckDB file path. An alert webhook such as `SLACK_WEBHOOK_URL` would be an Airflow Variable or Connection, set in the UI or through `AIRFLOW_VAR_SLACK_WEBHOOK_URL` in `.env`, and read with `Variable.get()`. `.env` and `airflow_settings.yaml` are in `.gitignore`. A secret in a DAG file ends up in Git history forever, is visible to everyone with repo access, can be scraped from public GitHub within minutes, and has to be rotated once leaked. Production would use a secrets backend such as Vault or AWS Secrets Manager.
8. **Audit.** Example: rejected order **ORD000469**.
   - *ETL:* `include/quarantine/slick/orders_failed_<run_id>.csv` contains the row exactly as read (`ORD000469,2026-09-07 11:52:46,C00076,S02,P0041,0,444.0,10,0.0,...,orders.csv,127,orders_quantity_positive`), with source file, line 127 and the rule broken. `SELECT * FROM etl_rejected_rows WHERE row_key = 'ORD000469'` returns the same. `SELECT COUNT(*) FROM etl_fact_orders WHERE order_id = 'ORD000469'` returns **0**, so it is not in any revenue total.
   - *ELT:* `SELECT * FROM raw_orders WHERE order_id = 'ORD000469'` shows it exactly as received (all text, quantity `0`). `SELECT dq_status, failure_reason FROM stg_orders WHERE order_id = 'ORD000469'` returns `FAIL / orders_quantity_positive`. `SELECT COUNT(*) FROM mart_fact_orders WHERE order_id = 'ORD000469'` returns **0**.
   - ELT answers it in one place with SQL. ETL needs the file plus the database.
9. **Change history.** Example: ORD000271 was DELIVERED on 4 September (₹445) and RETURNED in the 1 October increment.
   - After the incremental load, **both pipelines show it as RETURNED**, so September revenue drops from ₹1,134,962.80 to ₹1,130,769.10 (-₹4,193.70, which is exactly the 10 returns; they also appear in the reconciliation as `RETURNED_NOT_REFUNDED`) for the 10 returns (`net_revenue` is 0 once RETURNED). The 150 new orders are dated 1 October and don't touch September.
   - Finance normally wants **both** views:
     - an "as reported" September figure that never changes after month close;
     - an "as of today" figure with the return applied, booked as an October adjustment.
   - ETL keeps only the latest state, so the old value is overwritten and lost. ELT still holds both versions in `raw_orders` (same order_id, different `_source_file` and `_loaded_at`), so a `snap_orders` table, an SCD Type 2 table with `valid_from`/`valid_to`, can be rebuilt from raw at any time.
   - We also observed that a normal run after the increment (the daily `orders.csv` only) overwrites the 10 orders back to DELIVERED in both pipelines, because the full file is newer. The fix is to apply changes in event-time order: keep the `_loaded_at` history and never let an older status overwrite a newer one.

### Five pillars

| Pillar | What my pipelines do | Coverage |
|---|---|---|
| Freshness | `orders_latest_order_fresh` warns when the newest order is more than 1 day old (Experiment 9); `pipeline_runs.end_time` shows when data was last refreshed; schedule at 9:00 with a 10-minute timeout | Medium: warns but doesn't alert anyone |
| Volume | rows in, passed and quarantined per file in the logs; `pipeline_runs` row counts; `orders_volume_drop_lt_90pct` warns below 10% of the 7-run median (Experiment 7) | Good |
| Schema | ETL `read_source` and ELT `extract_*` check expected columns; `INSERT ... BY NAME` fails on any drift (Experiment 6) | **Strongest**: fails loudly before anything loads |
| Distribution | Only indirectly: accuracy rules (formula, ranges) catch broken values. A real price change with a matching amount would pass (Experiment 8) | **Weakest**: no statistical drift check (for example average order value per store vs the last 7 days) |
| Lineage | ELT: `_source_file`, `_source_row`, `_run_id` from raw through `mart_fact_orders`; ETL: only for quarantined rows | Good in ELT, partial in ETL |

**Strongest:** schema, which fails loudly with a clear error. **Weakest:** distribution, which has no statistical check and no alert channel. Next steps are a per-store average-price/AOV drift check in `dq_results`, and an email or Slack alert on FAIL or WARN.

## Part G: Recommendation to Sameer (CTO)

**To:** Sameer, CTO, NammaMart. **From:** FDE team. **Subject:** ETL or ELT for the 9 AM report.

**Recommendation: adopt ELT** (raw, then staging, then marts in SQL), and keep the ETL's strict quality gate inside it. Finance's dashboards read only marts, and marts are built only from rows with `dq_status = 'PASS'`.

**What we observed (same data, both pipelines run side by side, plus 10 failure experiments on each):**

- **Same numbers.** On the September data and after the 1 October increment, both pipelines produced identical totals: 2,458 clean orders, ₹1,210,421.30 net revenue, ₹215,792.95 unreconciled, the same 154 rejected rows. Choosing ELT costs no accuracy.
- **Data quality guarantee.** Both are equally strict. The same 44 checks, written once, run in both. In every bad-data experiment (null customer, negative quantity, unknown store, `SHIPPED`, 2027 timestamp) the row was blocked from revenue in both. ETL gives the guarantee physically (bad rows never reach the warehouse). ELT gives it by rule (marts filter on `dq_status`). That rule is one line of SQL in one file, so it is easy to review.
- **Auditability.** This is where ELT wins clearly. ELT keeps every row exactly as received, with file, line and run. Finance's audit question ("show the rejected order as received, the rule, and prove it's excluded") is three SQL queries in one database. ETL needs a CSV file from the quarantine folder plus the database, and for loaded rows it cannot trace back to the source line at all. ELT also kept both versions of the 10 returned orders, so we can rebuild "September as reported" later. ETL overwrote them.
- **Ease of change.** In ELT a new business question or a corrected rule is a new or edited SQL file, replayed over the stored raw history with no re-extract. Analysts can read and review SQL. ETL changes need Python changes and the original files.
- **Performance at 1000x (~2.4M orders/month).** Both ran in about 30 seconds today. ETL loads everything into pandas in one worker's memory, which won't scale far past a few GB. ELT pushes the work to the database engine. DuckDB handles 1000x on one machine, and the same SQL moves to Postgres, BigQuery or Snowflake later. Raw grows on every run (we saw 2,412, then 4,824, then 7,396 order rows after 3 runs), so raw needs date partitioning and incremental loading by `_loaded_at` instead of full snapshots.
- **Cost.** Both are fully open source (Airflow, DuckDB, pandas). ELT stores more (raw history and staging), but at NammaMart's size that is megabytes, and object storage is cheap. ETL is cheaper only if storage is very expensive, which it isn't.

**Top 3 risks of the ELT design, and mitigations**

1. **PII exposure in raw.** `raw_customers` holds unmasked phone and email forever. Mitigation: separate schema with restricted access, column encryption, DPDP-compliant retention and erasure jobs.
2. **A mart that skips the `dq_status = 'PASS'` filter would leak bad rows to Finance.** Mitigation: every mart reads from `mart_fact_orders` (already filtered), code review for SQL, and a test that mart totals equal the clean-fact totals.
3. **Raw growth and snapshot semantics.** Full daily snapshots duplicate data, and an old full file can overwrite a newer correction (we saw this in testing). Mitigation: incremental, date-partitioned loads, latest-version-wins by event time, and an SCD-2 orders snapshot for history.
